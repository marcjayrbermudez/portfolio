Problem-Solving

Bugs I found and fixed while building my projects. Click a case to read it.

Problem: When I cancelled an order in My Orders, the sneakers in that order were not added back to the stock. The shop still showed "Only 3 left" even though nothing was sold.

Possible Causes: The cancel button only changed the order status, the stock was not updated, or the shop page was not redrawn after cancelling.

Diagnostic Procedure: I added an item to the cart, placed the order, and checked the stock label. Then I cancelled the order and checked again. I read the code of the cancel button and saw that it only set order.status = "Cancelled".

Solution: In the cancel button, I looped through the items of the order and added each quantity back to the product's stock, then called renderProducts() to update the shop page.

Lesson Learned: When one action changes the data, I must update every related part, not just the one I see. Testing the full flow (order, then cancel, then check) helps find these bugs.

Problem: After placing an order, the stock was correct. But when I refreshed the page, all sneakers showed full stock again.

Possible Causes: The stock was only changed in memory, the orders were not saved, or the saved orders were not used when the page loads.

Diagnostic Procedure: I opened DevTools (F12), went to Application, then Local Storage, and saw that the orders were saved correctly. So the problem was that the product list in products.js always starts with the original stock.

Solution: When the page starts, the app now goes through all saved orders that are not cancelled and subtracts their quantities from the stock.

Lesson Learned: Data in a variable is lost on refresh. Only the data saved in localStorage stays, so the app must rebuild its state from the saved data when it starts.

Problem: When I edited a student's grades and clicked Save, the app showed "That student number is already in the list," even though I did not change the student number.

Possible Causes: The duplicate check was comparing the student with themselves, or the edit was being treated as adding a new student.

Diagnostic Procedure: I tested adding a new student (it worked) and editing a student (it failed). Then I read the validate() function and saw that it checked every student in the list, including the one being edited.

Solution: I changed the check so it skips the student being edited, using s.id !== editingId. Now editing works, and real duplicates are still blocked.

Lesson Learned: Validation rules can be different when adding and when editing. I should test both cases.

Problem: While testing, I expected a final grade of 87.90 to be 1.75, but the app showed 2.00.

Possible Causes: A wrong formula for the final grade, a rounding problem, or a mistake in my own expected answer.

Diagnostic Procedure: I computed the final grade by hand: 85 × 0.30 + 88 × 0.30 + 90 × 0.40 = 87.90, so the formula was correct. Then I checked the grading scale: 1.75 starts at 88, so 87.90 really belongs to 2.00.

Solution: The app was correct and my test was wrong. I fixed my test and added the full grading scale to the app and the README so the rules are clear.

Lesson Learned: Before fixing code, I should check if my expected result is really correct. Computing by hand is a good way to check.

Problem: A task due on October 22 could be shown as due one day earlier, and today's tasks could be marked as overdue.

Possible Causes: Wrong date format from the date picker, or the time zone. JavaScript reads a date like "2026-10-22" as midnight in UTC, which is 8 hours behind Philippine time.

Diagnostic Procedure: I printed new Date("2026-10-22") in the Console and saw that it was not midnight in Philippine time, so the date moved when it was formatted.

Solution: I split the date into year, month, and day and made the date with new Date(y, m - 1, d), which uses local time. For overdue tasks, I compare dates as text in the same "YYYY-MM-DD" format, which works without time zones.

Lesson Learned: Dates and time zones can cause hidden bugs. The Console is a quick way to see what a value really is.

Cybersecurity Case Study: SQL Injection

A beginner-level look at a common website weakness and how to prevent it.

1. What is the vulnerability?

SQL injection is a weakness in websites that use a database. It happens when the website puts whatever the user types directly into a database command (SQL query). An attacker can type special text that changes the command and makes the database do something it should not do.

2. How can it happen?

For example, a login form takes the username and password and builds a query by joining text together. If someone types ' OR '1'='1 in the password box, the query becomes always true, and they may log in without the correct password.

Unsafe (do not use):

$sql = "SELECT * FROM users
  WHERE username = '" . $_POST['user'] . "'
  AND password = '" . $_POST['pass'] . "'";

3. What are the risks?

  • Logging in as another user without a password
  • Stealing private data like names, emails, and passwords
  • Changing or deleting records in the database
  • Breaking the Data Privacy Act of 2012 if personal data leaks

4. How can developers prevent it?

Use prepared statements. The query is written first with a placeholder (?), and the user's input is sent separately as plain data, so it cannot change the command.

Safe:

$stmt = $conn->prepare(
  "SELECT * FROM users WHERE username = ?");
$stmt->bind_param("s", $_POST['user']);
$stmt->execute();

5. What security practices should be implemented?

  • Use prepared statements for every query with user input
  • Check user input (type, length, allowed characters)
  • Save passwords as hashes, never as plain text
  • Show simple error messages to users, not database errors
  • Give the database account only the permissions it needs
  • Test only on my own system, never on other people's websites

Reflection

My path to IT did not start with computers. In senior high school at Parañaque National High School, I took the HUMSS strand, where I learned to communicate, think critically, and understand people. When I entered the BSIT program at Datamex College of Saint Adeline in 2024, everything felt new. I had to start from zero, but I found that the skills I learned in HUMSS still helped me, especially in explaining ideas and working with others.

The most important thing I learned in BSIT is how to think like a programmer. Learning programming logic, such as variables, conditions, loops, and functions, taught me to break a big problem into small steps. Studying PHP, Python, Java, and C++ showed me that each language looks different, but the logic behind them is the same. Once I understood that, learning a new language became less scary.

Building this portfolio website was one of my most useful experiences. I used HTML, CSS, and JavaScript to create my own page, add my skills and certificates, and make it work on both phone and desktop. It was the first time I saw my own work online in one place, and it made me want to build more.

My biggest challenge was not giving up when my code did not work. At first, errors made me frustrated. Over time, I learned to read the error message, test one small part at a time, and check the simple things first. I also learned that AI tools can help me learn faster, but I must still understand, test, and check my own work instead of just copying an answer.

Outside the classroom, I joined webinars on Arduino, website building, Linux, network security, and digital office skills. They showed me how wide the IT field is and helped me see that Software Engineering is the path I want to focus on.

I know that I am still a beginner. I want to get better at programming, especially in building complete projects, learn to use Git and GitHub well, and improve my MySQL skills. My plan is to practice coding regularly, build small projects on my own, and ask for feedback from my teachers and classmates.

My goal is to become a Software Engineer who builds reliable programs that solve real problems. I want to start in an entry-level or trainee role, where I can learn from experienced developers and grow step by step. I may not know everything yet, but I am willing to learn, I work well with others, and I do not give up easily.
